# Видео: источники, права и техническая обработка

Проверено: 2026-11-04. Это исследование Phase 0; загрузчик, перекодирование и воспроизведение ещё не реализованы. Медиа и исполняемые файлы не скачивались. Проверка страниц не равнозначна проверке файла, его целостности или визуального содержания.

## Вывод по первоначальному наполнению

Автоматическую первоначальную загрузку трёх требуемых категорий пока нельзя объявить обеспеченной. Найдены два конкретных кандидата для pressure washing, но не проверенный стартовый набор soap cutting и Subway Surfers с подтверждёнными правами. Это обязательный критерий Phase 2 и блокер готовности автоматического наполнения, а не причина подменять категории случайными видео.

## Лицензия и способ доставки — разные проверки

[Pexels License](https://www.pexels.com/license/) разрешает бесплатное использование и изменение фото и видео; запрещает, среди прочего, подразумеваемое одобрение продукта изображёнными людьми/брендами и распространение на других стоковых/wallpaper-площадках. Лицензия контента не освобождает от правил автоматизированного доступа. Не считать обычную ссылку на скачивание доказательством разрешения массового скачивания.

[Pexels API](https://www.pexels.com/api/documentation/) требует авторизацию, обратную ссылку и соблюдение правил использования. В правилах есть ограничение на воспроизведение основной функциональности Pexels, включая wallpaper-приложения. Поэтому API не принимать как бесспорный базовый канал для Brainrot: до реализации проверить применимость и при необходимости получить разъяснение Pexels. Нельзя встраивать общий секретный API-ключ в open-source приложение. Ключ пользователя — только необязательный дополнительный источник, не замена первоначальному наполнению без аккаунта.

[Pixabay Content License Summary](https://pixabay.com/service/license-summary/) допускает бесплатное использование и адаптацию, но ограничивает распространение содержимого без самостоятельного творческого вклада. Простое перекодирование нельзя автоматически считать таким вкладом. Сводка указывает на обязательность полных условий и возможные права третьих сторон. Pixabay не выбран для зеркала исходных видео или готового downloadable pack без дополнительной проверки.

Рекомендуемое основание для автоматического стартового набора: собственная съёмка проекта с явным разрешением на доставку/изменение либо индивидуальные CC0/CC BY материалы, прошедшие проверку. Не требуется сервер с LLM или MCP. Если публикация проверенных копий разрешена, нужен статический HTTPS-каталог и хранилище медиа отдельно от Git, без исполняемого кода. Это проектное предложение; пока такого каталога нет.

## Каталог и fallback для Phase 2

Каждый одобренный элемент должен фиксировать: `id`, категорию, автора, исходную страницу, лицензию и её URL, дату проверки, основание автоматической загрузки/изменения/распространения, обязательную атрибуцию, точные URL загрузки и запасного источника, SHA-256 конкретного файла, размер и проверенные параметры. Для пользовательских записей хранить тип `user-import` и не публиковать путь/данные пользователя.

Повторно проверять права и доступность при изменении источника или версии каталога. Не допускать перехода на произвольные домены из перенаправлений. Загружать потоково в `.TMP`, с ограничением размера, таймаутом и конечным числом попыток; после проверки переносить в локальный кеш внутри `.TMP`. SHA-256 проверяет соответствие ожидаемому файлу, а не законность содержания. Лицензии и кредиты показывать в UI и сохранять рядом с кешем.

Fallback: исправный локальный кеш → другой заранее одобренный элемент той же категории → явное предложение импорта. При отсутствии контента показывать пустой слот с причиной, сохранять управление остальными слотами. Не подставлять другое видео под неверной категорией. При офлайн-запуске не блокировать приложение. Нельзя снимать DRM, обходить логин/ограничения или использовать YouTube-скачивание как универсальное решение.

## Desktop-движок: рекомендация

Для общего companion-приложения рекомендуется Electron + TypeScript + обычный HTML/CSS, три независимых HTMLVideoElement, локальный каталог и минимальный preload API. Это архитектурный выбор, не измеренная производительность. Electron позволяет загружать локальный интерфейс и управлять собственным окном через [BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window). Его `parent` — другое собственное BrowserWindow; этот API не делает окно дочерней панелью внешнего Claude/Codex. Оконное следование внешнему приложению потребует отдельной документированной платформенной реализации и проверки; ручное расположение рядом остаётся честным fallback.

[Electron protocol](https://www.electronjs.org/docs/latest/api/protocol) поддерживает собственные схемы и потоковое аудио/видео через привилегии схемы. План: `brainrot-media://<opaque-id>`, разрешение только известных ID в approved roots, без произвольных абсолютных путей/обхода каталогов. Не включать `bypassCSP`. Проверить Range/seeking и обработку ошибок на целевой версии. HTTP-сервис для локального воспроизведения не нужен.

По [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security) интерфейс должен быть локальным, с sandbox/contextIsolation, без Node в renderer, с узким валидируемым IPC, строгим CSP и запретом произвольной навигации. Само видео не должно становиться поводом загружать исполняемый remote UI.

Tauri остаётся допустимой альтернативой с меньшим пакетом, но использует разные системные WebView: [Webview Versions](https://v2.tauri.app/reference/webview-versions/) описывает WebView2 на Windows и WebKit на других настольных платформах. [Windows Installer](https://v2.tauri.app/distribute/windows-installer/) описывает варианты доставки WebView2. Вывод проекта: Electron уменьшает вариативность движка при трёх видеопотоках и позволяет единый JS/TS стек; цена — размер пакета и память. Не утверждать, что Tauri не поддерживает нужное видео.

Для Phase 1 целевой нормализованный формат — WebM/VP9 без звука, с ограничением разрешения/fps. Дополнительно проверить MP4/H.264 конкретной поставки и машины; не обещать поддержку любого пользовательского контейнера. Нужны реальные проверки `canPlayType`, `loadedmetadata`, роста `currentTime`, loop и одновременного декодирования на Windows. Никаких API-ключей/вызовов LLM для цикла проигрывания.

## FFmpeg и проверка медиа

[ffprobe](https://ffmpeg.org/ffprobe.html) даёт машинно-читаемые сведения о контейнере/потоках. Сначала проверить код возврата, существование видеопотока, длительность и размеры. Это не полная проверка декодирования: в Phase 2 отдельно прогнать файл через декодирование до конца с [ffmpeg](https://ffmpeg.org/ffmpeg.html) в null output и таймаутом. Нормализация должна выбирать только первый видеопоток, исключать аудио, субтитры и вложения, ограничивать ресурсы, а не исполнять команды из метаданных. Запуск — массив аргументов без shell.

[FFmpeg Download](https://www.ffmpeg.org/download.html) сообщает, что проект распространяет исходники, и отдельно перечисляет Windows-сборки gyan.dev/BtbN. Для Phase 2 сначала использовать уже установленную проверенную утилиту; при необходимости автоматической установки выбирать зафиксированную сборку из документированного канала с проверкой хеша, не случайный EXE.

[FFmpeg Legal](https://ffmpeg.org/legal.html) различает LGPL и сборки с GPL-компонентами. До включения бинарников в установщик проверить configure flags, точные лицензии и исходники поставки; MIT-лицензия собственного кода не покрывает FFmpeg и видео. Эти действия остаются в Phase 2/6.

## Критерии, которые ещё не выполнены

- Нет трёх одобренных категорийных стартовых файлов и собственных SHA-256.
- Нет проверки разрешённости автоматического канала Pexels для данного продукта.
- Не выполнены загрузка, ffprobe, декодирование или воспроизведение кандидатов.
- Не измерены CPU/GPU/RAM трёх одновременных потоков.
- Не проверены аппаратное ускорение, RDP, Windows N/KN, система без медиа-компонентов и Windows ARM64.
- Не выбрана и не протестирована конкретная версия Electron/FFmpeg; версии фиксировать при начале соответствующего этапа, не выдумывать в исследовании.
